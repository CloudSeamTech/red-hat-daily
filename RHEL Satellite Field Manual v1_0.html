Section 00

The Big Picture & the Words You'll Hear

Why this setup exists, and a plain-English translation of the jargon so the rest of the manual makes sense.

Two Satellites, and content moves as files

You have two Satellite servers:

  • Connected Satellite (low side) — the only box allowed to talk to Red Hat. It downloads all the packages and container images.
  • Disconnected Satellite (high side) — the classified box. Never touches the internet. It only gets content as files you carry over.

Everything moves as a file: export a bundle on the low side → transfer it across the guard/diode → import it on the high side. Your users just point their machines at the high-side Satellite and never know the difference.

◆ The one rule that matters

A snapshot is not a backup (see Section 13). And on Satellite, patching isn't done box-by-box — it's importing content, publishing a new Content View version, and promoting it. Keep those two ideas in mind and the rest clicks.

Section 02

Repos & Content Sync (the core job)

Pull updates + containers on the connected side, carry them across the gap, import them on the classified side. This is most of what you're there to do, and it runs every patch cycle.

▸ What is "YourOrg"?

Not a fixed Red Hat name — it's whatever your site named its Organization in Satellite. A built-in "Default Organization" exists, but most shops make their own. Run hammer organization list and use that exact name.

Step A — on the CONNECTED (low-side) Satellite

First time (a full baseline copy of a bundle):

hammer content-export complete version \ --content-view "RHEL9-Base" --version "1.0" \ --organization "YourOrg" --format importable

Every time after (only the new stuff — faster and smaller):

hammer content-export incremental version \ --content-view "RHEL9-Base" --version "2.0" \ --organization "YourOrg" --format importable

What each part means

complete
Export EVERYTHING (use the first time).
incremental
Export only what changed since last time (use every time after).
--content-view
Which approved bundle to export.
--version
Which numbered snapshot of that bundle.
--organization
Your org name in Satellite.
--format importable
MUST use this to include CONTAINERS. (The other option, 'syncable', is packages-only.)
--chunk-size-gb 5
Optional — splits the output into 5 GB pieces if your transfer method has a size cap.

Output lands in /var/lib/pulp/exports/ — grab the tarball and the .json file next to it.

◆ Same-version rule

For 'importable' (containers), both Satellites must be on the same version, or the export silently won't import. Check both before you start.

Step B — carry it across

Move the tarball + .json across your guard/diode/media, following your site's transfer rules.

Step C — on the DISCONNECTED (high-side) Satellite

Drop the files into the import folder (must be here, owned by the pulp user):

/var/lib/pulp/imports/ # owner must be pulp:pulp

Then import:

hammer content-import version \ --organization "YourOrg" \ --path /var/lib/pulp/imports/YourExportDir

'importable' auto-creates the products, repos, and Content View if they don't exist yet. Then publish/promote the CV and your clients pick it up.

One-time setup on the disconnected side

Do these ONCE before your first import, or it fails:

  1. Upload the license (manifest) you carried over:
    hammer subscription upload \ --file /path/manifest.zip --organization "YourOrg"
  2. Make sure your account has the Content Importer role.
  3. Make sure /var/lib/pulp/imports/ exists and is owned by pulp:pulp.

Section 03

Containers: Serving Images to Others

Good news: containers ride inside the same import from Section 02 — there's no separate pipeline to run.

On the low side you sync the container repos into a Product and add them to the Content View like any other repo. Once imported and promoted, your high-side Satellite IS the registry. Clients pull like this:

podman login satellite.example.com podman pull satellite.example.com/yourorg-product-repo:tag

Three things that trip people up

CA trust
Each client needs the Satellite CA cert at /etc/containers/certs.d/<satellite>/ca.crt or the pull fails on TLS.
Ugly names
The default image name is org-product-repo mashed together. Set a Registry Name Pattern on the CV to give people a clean pull path. Do this on day one.
Auth
podman login auto-creates a token. Or turn on Unauthenticated Pull on a lifecycle environment (e.g. Production) so people can pull with no credentials.

Section 04

Patching (this changed since RHEL 7)

dnf replaced yum (yum is just a shortcut to dnf now). On Satellite, patching is a "promote-and-pull" flow, not a per-box chore.

On a single box

# what updates are waiting? dnf check-update # just the security fixes, if you only want those dnf updateinfo list security # apply everything Satellite is offering (type y to confirm) dnf update # did it change the kernel/core libs? -r = "do I need a reboot?" dnf needs-restarting -r

On Satellite (the real model)

You don't patch each box by hand. Patching = import new content → publish a new Content View version → promote it through Dev/Test/Prod → clients pull the new errata. The export/import cycle in Section 02 is your patching.

▸ Two models — ask which one this site uses

Some shops push patches for you from Satellite (Remote Execution or errata apply) so you never log into each box. That decides whether the box commands above are your job or automatic.

Major upgrade: RHEL 8 → 9 with Leapp

Jumping a whole major version (8 → 9) is not a dnf update — you use Red Hat's Leapp tool, which upgrades in place across a special reboot. It's riskier than patching, so snapshot the VM first (Section 13).

✕ Snapshot before you start

In-place major upgrades can fail halfway. Take a vCenter snapshot (and/or a full backup) first so you can roll straight back.

# 1) be on the latest 8.x minor first, then install Leapp (from Satellite) dnf update dnf install -y leapp-upgrade # 2) pre-upgrade assessment — finds everything that will block you leapp preupgrade # 3) READ the report and fix every "Inhibitor" item less /var/log/leapp/leapp-report.txt # 4) once the report is clean, run the upgrade, then reboot leapp upgrade reboot # boots a special upgrade environment; it reboots itself again after
leapp preupgrade
Dry-run check. Writes the report to /var/log/leapp/leapp-report.txt — nothing is changed yet.
Inhibitor
A hard blocker. The upgrade won't run until every one is resolved. High/Medium/Low are warnings only.
leapp upgrade
Does the real work — stages the RHEL 9 packages. The upgrade itself happens during the reboots.
--target 9.x
Aim at a specific minor (e.g. 9.6). Add --no-rhsm if you're not using direct RHSM.

The errors you'll likely hit (why an upgrade "won't go")

Third-party packages
Anything not signed by Red Hat that shares a name with a RHEL package inhibits the upgrade — the #1 blocker on app boxes.
Disk space
Not enough free space on / or /boot. Free some first (Section 09).
Deprecated drivers
Old kernel drivers and settings (e.g. firewalld AllowZoneDrifting) get flagged — the report gives the fix.
Config-mgmt agents
Disable Puppet/Salt/Chef and agent-based tooling during the upgrade.

◆ For appliance apps like Tenable Security Center

Third-party "appliance" software (Security Center, Nessus, some agents) ships packages Leapp can't vet, so an in-place 8→9 often keeps failing on those inhibitors. For these, the vendor-supported path is usually a clean RHEL 9 build → reinstall the app → restore its config/data, not Leapp. Check the vendor's RHEL 9 guidance before fighting the inhibitors — a fresh build from a template (Section 19) is often faster and cleaner. That's very likely what's biting your Security Center box.

Section 05

User Accounts (local)

How to create, change, and remove accounts on a single box — and the "no-login" service accounts you'll set up for software. Think of a user account as a name badge plus a home office (their home folder) plus a set of door keys (their groups).

▸ Local vs IDM accounts

On an IDM-joined box, real people usually log in with IDM accounts (Section 06). The local useradd commands here are mostly for service accounts that run software — nobody logs in as them.

Where accounts actually live (the files to check)

/etc/passwd
The list of accounts: username, ID, home folder, and login shell. (No passwords here despite the name.)
/etc/shadow
The encrypted passwords and expiry info. Root-only.
/etc/group
The groups and who's in them.
/home/<user>
Each person's home folder (their files, settings).
/etc/skel
The "starter kit" — its contents get copied into every new home folder you create.
/etc/login.defs
Defaults for new accounts (ID ranges, password aging).
/etc/sudoers.d/
Drop-in files that grant sudo (admin) rights. Edit with visudo.

Create a normal user (a person who logs in)

useradd -m -s /bin/bash -c "Jane Doe" jdoe passwd jdoe # set their first password
-m
Make their home folder (copies from /etc/skel). Without it, they have no home.
-s /bin/bash
Their login shell — the command prompt they get. bash is the normal one.
-c "..."
A comment, usually their full name.
-d /path
Use a custom home folder location instead of /home/<user>.
-G grp1,grp2
Add them to extra groups (e.g. wheel for sudo rights).
-u 1234
Force a specific user ID number (rarely needed).
passwd jdoe
Sets/changes their password. They can't log in until this is done.

Create a "no-login" service account

Software (a database, an app) should run as its own account that nobody can log into. The trick is giving it a fake shell called nologin — if someone tries to log in as it, the door just closes.

useradd -r -s /sbin/nologin -M appsvc
-r
Make it a system account (low ID number, no aging) — the convention for service accounts.
-s /sbin/nologin
The "no shell" shell. Blocks interactive login. This is the key part.
-M
Do NOT make a home folder (a service usually doesn't need one).

Change an existing user

# give someone sudo rights: add them to the wheel group usermod -aG wheel jdoe # lock / unlock an account (block login without deleting it) usermod -L jdoe # lock usermod -U jdoe # unlock

◆ The -a is critical

usermod -aG adds a group. usermod -G without the -a replaces all their groups — you'll accidentally kick them out of every other group. Always include -a when adding.

Delete a user

userdel -r jdoe
-r
Also delete their home folder and mail. Without -r, the account is gone but their files stay behind.

Groups (sets of door keys)

groupadd devs # make a new group gpasswd -a jdoe devs # add a user to it gpasswd -d jdoe devs # remove a user from it groupdel devs # delete the group

Verify your work (always check after)

id jdoe # their IDs + every group they're in getent passwd jdoe # their account line (works for IDM users too) groups jdoe # just the group names ls -la /home/jdoe # confirm the home folder exists and is theirs

Section 06

IDM Accounts & SSH Keys

How login really works: you make a key pair on YOUR machine. One half is private and never leaves your laptop; the other half is public and safe to hand out.

ssh-keygen -t ed25519 -C "ian@admin"
-t ed25519
The key type (modern, strong, short). RSA also works if a system requires it.
-C "..."
A label so you know whose key it is.

That makes two files: ~/.ssh/id_ed25519 (PRIVATE — guard it) and ~/.ssh/id_ed25519.pub (PUBLIC — upload this one).

Attach your PUBLIC key to your IDM account

Web UI: Identity → Users → you → add SSH public key. Or CLI:

ipa user-mod ian --sshpubkey="ssh-ed25519 AAAAC3Nz...your_pub_key..."

Now SSH into any IDM-enrolled box. The box asks IDM for your public key; your private key proves it's you. No copying keys onto each server.

ssh ian@web01.example.com

How the admin account gets created

First admin
Auto-created when the server was first built with ipa-server-install (it prompts for the admin password then). It already exists — you don't make it.
New admins
An existing admin creates the user, then adds them to the 'admins' group for full rights:
ipa user-add jsmith --first=John --last=Smith ipa group-add-member admins --users=jsmith

✓ Old-school contrast

ssh-copy-id shoves your key into ONE box's authorized_keys file — the non-IDM way. With IDM you attach the key once to your account and it works everywhere.

Section 07

DNS & BIND (how names resolve in an IDM shop)

IDM runs its own DNS, and under the hood that DNS server IS BIND (named). But you don't hand-edit BIND zone files here — you manage DNS through IDM, and it keeps BIND in sync.

◆ Why it's built this way

Kerberos (what makes IDM logins work) demands that BOTH directions of DNS are correct, or enrollment, logins, and certificates quietly break.

A record
Forward: name → IP. e.g. web01.example.com → 10.1.1.50
PTR record
Reverse: IP → name. e.g. 10.1.1.50 → web01.example.com

Best command — add a host AND both records in one shot

ipa host-add web01.example.com --ip-address=10.1.1.50

Other useful DNS commands

# list the DNS zones IDM manages ipa dnszone-find # add an A record and auto-build its reverse (PTR) at the same time ipa dnsrecord-add example.com web01 \ --a-rec=10.1.1.50 --a-create-reverse # see all records in a zone ipa dnsrecord-find example.com
--a-create-reverse
Automatically builds the matching PTR record so you don't have to do it by hand. Big time-saver.

Always verify BOTH directions with dig

dig web01.example.com # forward: should return the IP dig -x 10.1.1.50 # reverse: should return the name

New box / new person, start to finish

  1. ipa host-add ... --ip-address= → creates the host plus its A and PTR records.
  2. On the new box: ipa-client-install → joins it to IDM (Kerberos, SSH, sudo).
  3. dig both ways to confirm the name resolves.
  4. For a person: ipa user-add, attach their SSH key (Section 06), then add them to the right group so they're allowed onto that host.

Section 08

Firewall · Ports · Logs

The three tools that answer "why can't I reach this service?" and "what broke?" Learn to use them together.

Firewall (firewalld) — the locked door

The firewall decides which ports the outside world can reach. A service can be running perfectly and still be unreachable because its door is locked.

firewall-cmd --list-all # what's currently open firewall-cmd --permanent --add-port=9090/tcp # open a port (here: Cockpit) firewall-cmd --permanent --add-service=https # or open by service name firewall-cmd --reload # apply the saved changes
--permanent
Saves the rule so it survives a reboot. Without it, the change is temporary and vanishes on restart.
--add-port=9090/tcp
Open a specific port number and protocol.
--add-service=https
Open a known service by name (firewalld knows https = 443).
--reload
Firewalld only starts using --permanent rules after this. Easy to forget.

Ports & sockets — the "who's listening?" check (ss)

A socket is just a live network connection or a service sitting and waiting for one. ss ("socket statistics") shows you every one. You run it to answer: is my service actually up and accepting connections, and on which address/port?

ss -tulpn

What each letter means and why it's there

-t
Show TCP sockets — the protocol almost all services use (web, SSH, databases).
-u
Show UDP too — needed for things like DNS (port 53).
-l
Only show listening sockets — services waiting for connections. This is the key filter: it answers "what's running and open?"
-p
Show the program (process) that owns each port — so you know what is listening.
-n
Show numbers, not names (22 instead of "ssh"). Faster and avoids confusion.

How to read the output

The columns that matter are the Local Address:Port (where it's listening) and the process name at the end. The address tells you who can reach it:

0.0.0.0:443
Listening on all interfaces — reachable from other machines. (* or [::] mean the same for "everywhere".)
127.0.0.1:443
Listening on localhost only — only this box can reach it. Outside connections will fail even with the firewall open.

What to DO once you've run it — the decision tree

Port missing
Your service's port isn't in the list → the service isn't running → start it: systemctl start <svc>, then check its logs below.
On 127.0.0.1
It's bound to localhost only → fix the app's config to listen on 0.0.0.0 or the real IP, then restart it.
On 0.0.0.0 but still unreachable
The service is fine → the firewall is blocking it → open the port with firewall-cmd above.

▸ The one-line rule

Service listening (ss) + port open (firewall) = reachable. If a connection fails, one of those two is missing. Check ss first, then the firewall.

Logs — finding out what broke (journalctl)

journalctl -u sssd # all logs for ONE service (swap the name) journalctl -xe # jump to the newest errors, with context journalctl --since "15 min ago" # only recent entries journalctl -f # live tail — watch messages appear as you test
-u <svc>
Filter to one service — the fastest way to see why it failed.
-x
Add extra explanation text to entries.
-e
Jump to the end (newest).
-f
Follow live — great while you reproduce a problem in another window.

Old-style files & app logs worth knowing

/var/log/secure
Login, SSH, and sudo activity (who got in, who failed).
/var/log/messages
General catch-all system messages.
Satellite
/var/log/foreman/production.log · run satellite-maintain health check
IDM
ipactl status · /var/log/dirsrv/ · /var/log/krb5kdc.log

Section 09

Storage: Add a vCenter Disk & Grow the Space (LVM)

LVM is three stacked layers. Learn the stack and the "grow" flow and you're set. (For the vCenter clicks that come first, see Section 10.)

PV
Physical Volume — a raw disk, prepped for LVM. The bottom layer.
VG
Volume Group — a POOL made of one or more PVs. Your bucket of free space.
LV
Logical Volume — a SLICE carved from the pool. It gets a filesystem and a mount point.

Flow to remember: new disk → PV → add to VG → grow LV → grow filesystem.

Full walkthrough: give a RHEL box more space from vCenter

  1. In vCenter: add a new virtual disk to the VM, or expand an existing one (Section 10 has the exact clicks). The disk comes from a datastore — the shared storage pool the VMs live on.
  2. Make Linux notice it (it won't see the change until you rescan):
    # brand-new disk — scans every SCSI bus so it's found wherever it landed: for h in /sys/class/scsi_host/host*/scan; do echo "- - -" > "$h"; done # (or, if the sg3_utils package is installed:) rescan-scsi-bus.sh # you GREW an existing disk instead? rescan just that disk: echo 1 > /sys/block/sdb/device/rescan lsblk # confirm the new/bigger disk now shows up
  3. Prep the disk for LVM (make it a PV):
    pvcreate /dev/sdb
  4. Add it to the pool (VG):
    vgextend datavg /dev/sdb # add to an existing pool # or, for a brand-new pool: vgcreate datavg /dev/sdb
  5. Grow the slice AND its filesystem in one shot — the -r flag resizes the filesystem for you (works for XFS and ext4):
    lvextend -r -l +100%FREE /dev/datavg/datalv # use all the new space # or a set amount: lvextend -r -L +50G /dev/datavg/datalv
  6. Confirm it worked:
    df -h # the mount should now show the bigger size
-r
Resize the filesystem together with the volume — saves a second command.
-l +100%FREE
Use ALL free space in the pool.
-L +50G
Use a specific amount instead.

◆ If you ever grow by hand

XFS (RHEL's default) grows with xfs_growfs <mountpoint> and can only GROW, never shrink. ext4 uses resize2fs <device>. Check your type first with df -T.

Tarballs, zipping & the right way to free space

A tarball is many files/folders bundled into one file — like packing a box. tar by itself just bundles; add gzip to also shrink it. The result is a .tar.gz (a packed, compressed box).

tar czf backup.tar.gz /path/to/folder # c=create z=gzip f=file tar tzf backup.tar.gz # t=list what's inside (peek without extracting) tar xzf backup.tar.gz # x=extract it back out
c / x / t
Create / eXtract / lisT — the three things you do with an archive.
z
Also gzip-compress it (shrinks it). Leave it off for a plain, uncompressed bundle.
f name
The archive filename to use.

A single file, or a cross-platform .zip instead:

gzip big.log # shrinks big.log -> big.log.gz (removes the original) gunzip big.log.gz # back to big.log zip -r archive.zip folder # make a .zip (Windows-friendly) unzip archive.zip

Space is full — is deleting really the best move?

First, find the hog — this is your go-to sequence:

du -sh /* # size of each top-level folder du -sh /var/* # then drill into the big one du -xh / | sort -rh | head # biggest items overall, staying on one filesystem

Now decide. Deleting frees space instantly, but it's the worst option if the data might matter — and in a classified or compliance shop, logs and data often have to be kept. Better choices, in order:

Compress it
A text log can shrink 80–90%. gzip big.log keeps the data but reclaims most of the space. Best when you must retain it.
Move it
If a whole folder is the problem, move it to a bigger volume and leave a symlink behind so everything still finds it (Section 15): mv /var/big /data/big && ln -s /data/big /var/big
Grow the volume
If it's real, growing data (like /var/lib/pulp), add space with LVM (top of this tab) rather than fighting it.
Delete — last
Only for true junk you're certain about. And remember: if a process still holds a deleted file open, the space won't come back until you restart it (lsof +L1).

Whatever you choose, confirm it worked with df -h afterward.

Moving, copying & removing files (and the rm -rf warning)

"Recursive" just means "and everything inside it, all the way down." A folder holds other files and folders, so any command that acts on a whole folder tree needs a recursive flag (-r). That one idea explains all the flags below.

Copy — cp

cp file.txt /path/to/dest/ # copy one file cp -r folder /path/to/dest/ # -r = copy a whole folder (needed for directories) cp -a folder /path/to/dest/ # -a = archive: copy AND keep permissions, timestamps, links cp -i file.txt /path/to/dest/ # -i = ask before overwriting an existing file
-r / -R
Recursive — required to copy a directory and its contents. Without it, cp refuses on a folder.
-a
Archive — preserves ownership, permissions, timestamps, and links. Use it for backups/migrations.
-i
Interactive — prompts before clobbering an existing file.

Move / rename — mv

mv old.txt new.txt # rename a file mv file.txt /path/to/dest/ # move a file mv folder /path/to/dest/ # move a whole folder — NO -r needed

Why mv needs no -r: on the same drive it just re-points the name (instant, even for a huge folder). Moving across drives, it copies then deletes for you. The same command renames and moves — there's no separate "rename."

Remove — rm (the dangerous one)

rm file.txt # delete one file rm -r folder # -r = delete a folder and everything in it rm -rf folder # -r + -f = recursive, forced, NO prompts, NO undo
-r
Recursive — required to delete a directory (rm alone won't touch folders).
-f
Force — skips every "are you sure?" prompt and ignores missing-file errors.
-i
Interactive — asks before each delete. Add it whenever you're not 100% sure.

✕ Why rm -rf can ruin your day

There is no recycle bin on the Linux command line — rm -rf erases an entire tree instantly and permanently, with no confirmation. The classic disasters are a stray space or an empty variable: rm -rf / home/ian (note the space before home) or rm -rf "$DIR"/ when $DIR is empty — both try to wipe the whole system. As root, that's catastrophic.

Safe habits before you rm -rf

  • Look first: run ls -la <path> to see exactly what you're about to delete.
  • Check variables: if the path uses $VAR, echo it first — an empty variable turns your command into a disaster.
  • Quarantine instead of delete: mv the folder to /tmp/quarantine/, confirm nothing breaks, then delete it later. Reversible.
  • Use -i when unsure: rm -ri <folder> prompts for each item.
  • Never blind-run rm -rf as root on a path you didn't just verify.

Why you DO use it: clearing a whole tree of genuine junk — old build output, a temp directory, a finished export — legitimately needs -r, and -f saves you from a thousand prompts when you're certain.

Big moves & migrations — rsync

For moving or copying large directory trees (especially to another drive — remember Section 15's "move it and symlink back"), rsync beats cp: it shows progress, resumes if interrupted, and preserves everything.

rsync -av /var/big/ /data/big/ # -a keep everything, -v show files rsync -av --progress src/ dest/ # add a live progress bar # after verifying the copy, remove the source and symlink it back: rm -rf /var/big && ln -s /data/big /var/big
-a
Archive — preserve permissions, timestamps, ownership, and links (the everyday default).
-v
Verbose — list what's being transferred.
trailing /
On the source, src/ means "the contents of src"; src (no slash) means "the folder src itself." This trips people up — be deliberate.

Section 10

vCenter: the Layer Under the OS

vCenter is the control panel for the virtual machines. Think of it as the box's "hardware" and power buttons. When the operating system can't help you — no SSH, no room to add a disk, the box won't boot — vCenter is where you go.

▸ Your environment

Section 12

Common Issues & How to Fix Them

Real scenarios you'll hit on-site. Each one: the symptom, the commands to check (in order), and the fix. Work top to bottom — the checks are ordered from most to least likely.

1. "The disk is full"

Symptom: writes fail, a service won't start, or you see "No space left on device."

Check

df -h # which mount is at 100%? du -xh /var | sort -rh | head # what's eating that mount? (swap /var) df -i # sometimes you're out of INODES, not space

Fix

journalctl --vacuum-size=500M # if logs are the hog, trim them # still full after deleting? a process may be holding a deleted file open: lsof +L1 | head # find deleted-but-open files; restart that service

If it's real data (like Satellite content in /var/lib/pulp), don't delete — grow the volume using Section 09.

2. "A service won't start"

Symptom: an app or daemon is down, or crashes right after starting.

Check

systemctl status httpd # is it running? what's the last error line? journalctl -xeu httpd # full recent logs for just this service ss -tulpn | grep 80 # is something ELSE already on its port?

Fix

Read the error at the bottom of status — it usually names the problem (bad config line, missing file, port in use). Fix that, then systemctl restart httpd. If a config was edited, test it first if the service offers a check (e.g. httpd -t).

3. "I can't SSH into the box"

Symptom: your connection times out or is refused.

Check (from the vCenter console — Section 10)

ip a # does it have an IP? is the network up? systemctl status sshd # is the SSH service even running? ss -tulpn | grep 22 # is it listening on port 22? firewall-cmd --list-all # is port 22 / the ssh service open?

Fix

No IP → network problem (check the interface / vCenter network settings). sshd down → systemctl start sshd. Listening but blocked → open it: firewall-cmd --permanent --add-service=ssh && firewall-cmd --reload.

4. "The box is slow / high load"

Symptom: everything drags; load average is high.

Check

uptime # load average — is it higher than your CPU count? top # press Shift+P (CPU) or Shift+M (memory) to sort free -h # is memory exhausted? is swap thrashing? ps aux --sort=-%cpu | head # the top CPU-hungry processes

Fix

Identify the hog and decide: restart it, kill it (kill <PID>), or add resources. If memory is the issue, check the journal for the OOM killer (journalctl -k | grep -i oom). If the host itself is overcommitted, confirm in vCenter's Monitor charts (Section 10) and add CPU/RAM there.

5. "Names won't resolve / DNS is broken"

Symptom: ping google-style names fail, or Kerberos/IDM logins break.

Check

cat /etc/resolv.conf # which DNS server is it using? dig web01.example.com # does a lookup work at all? resolvectl status # the active DNS config per interface ping -c2 10.1.1.10 # can you even reach the DNS/IDM server?

Fix

Wrong/missing DNS server → fix it (on IDM boxes it should point at the IDM server). Can't reach the DNS server → network/firewall issue. Records missing → add them in IDM (Section 07).

6. "IDM login fails but the password is right"

Symptom: your IDM account is rejected on one box; often a clock or cache problem.

Check

timedatectl # is the clock correct + synced? chronyc sources # is time sync actually working? systemctl status sssd # the service that talks to IDM id jsmith # does the box even see the IDM user?

Fix

Kerberos rejects logins if the clock is off by more than ~5 minutes — fix time first (systemctl restart chronyd). If the user isn't found, clear the cache and restart: sss_cache -E && systemctl restart sssd. Confirm DNS (Issue 5) since IDM depends on it.

7. "Filesystem went read-only"

Symptom: you suddenly can't write anywhere; apps error on save.

Check

dmesg | tail -40 # look for disk I/O errors near the bottom mount | grep ' ro,' # which mount flipped to read-only

Fix

This usually means the underlying disk had errors — check the datastore/disk health in vCenter (Section 10). After confirming the disk is healthy, a reboot often remounts clean; a damaged filesystem may need fsck on the unmounted volume (use the vCenter console for that).

vCenter-side issues

8. A vCenter alarm is red or yellow

Symptom: a red/yellow triangle on a VM, host, or datastore, or the alarm bell is lit.

Check

Click the object → Monitor → Issues and Alarms → Triggered Alarms and read what actually tripped. The usual suspects:

Datastore usage
Datastore over its % threshold → free space or expand it, and clean up old snapshots (they live on the datastore).
VM CPU/memory
Sustained high usage → Monitor → Performance; right-size the VM or find the hog inside the OS (Issue 4).
Consolidation needed
Leftover snapshot files → right-click the VM → Snapshots → Consolidate.
Host / uplink lost
A host or its network dropped → a host-level problem; check the ESXi host and its uplinks.

Fix

Fix the underlying cause first. Then clear the alarm: right-click it → Acknowledge ("I'm on it"), and once it's actually resolved, Reset to Green. Never reset to green without fixing it — that just hides the warning.

9. Can't reach a box at all — get in and power it on

Symptom: no SSH, no ping, and you're not even sure it's powered on.

Check & get in — work down this ladder

1. vCenter console
Right-click the VM → Launch Web Console. It works without the network. If it's simply off, right-click → Power → Power On, then watch it boot in the console.
2. vCenter down too?
Go straight to the ESXi host that runs the VM — the Host Client at https://esxi-host/ui. You can power on and console the VM from there without vCenter.
3. Host Client also out?
SSH to the ESXi host itself and power it on from the shell (commands below).
vim-cmd vmsvc/getallvms # list VMs + their IDs on this host vim-cmd vmsvc/power.getstate VMID # is it on or off? vim-cmd vmsvc/power.on VMID # power it on

Fix

Once you're on the console: if the OS is up but SSH was dead, fix it right there (Issue 3 — network, sshd, firewall). If it won't boot, read the screen for the error (bad /etc/fstab, a failed filesystem) and recover from the console.

▸ The universal first three

When something's wrong and you're not sure where to start: systemctl status <svc>, journalctl -xe, and df -h. Those three catch the majority of on-site problems.

Section 13

Backup & Restore (Veeam · vCenter · Satellite)

The safe order for patching a VM and getting it back if it breaks. Two safety nets: a snapshot (quick undo, delete after) and a Veeam backup (the real one you keep).

The order of operations

  1. Confirm a good Veeam backup exists — your real, keepable safety net.
  2. Take a vCenter snapshot right before patching — your instant undo for the next hour.
  3. Patch from Satellite (Section 04).
  4. Verify the box is healthy — services up, logins work, no errors.
  5. Healthy → delete the snapshot. Broken → roll back. Never leave a snapshot sitting around.

◆ Snapshot ≠ backup

A snapshot is a temporary undo point that grows the longer it lives and will hurt performance and fill your datastore if forgotten. Use it for the patch window, then delete it. Veeam is the backup you keep.

Back up in Veeam

A Veeam job quietly asks vCenter for a snapshot, copies the VM's data out, then removes its snapshot — leaving a full VM image in the repository. Confirm it's good before you touch anything:

  1. Open the Veeam Backup & Replication console → Home → Jobs (or Backups).
  2. Find this VM's job; look for a green Success on the last run. Red (failed) means no safety net — fix that first.
  3. To force a fresh one: right-click the VM → Start / Active Full, and wait for Success.

Take the vCenter snapshot

  1. vCenter → right-click the VM → Snapshots → Take Snapshot…
  2. Name it obviously: pre-patch 2026-08-25 (initials).
  3. Leave "Snapshot the VM's memory" unchecked for a normal patch (disk-only is cleaner and faster).
  4. Click OK — done in seconds. Write down the time so you remember to delete it.

Verify, then clean up

systemctl --failed # did anything fail to start after reboot? systemctl status sssd # key services running? (swap names) journalctl -xe # recent errors with context cat /etc/redhat-release && uname -r # confirm the new version took

Also do the real test: can you still log in with your IDM account, and does the app respond?

✓ Healthy → delete the snapshot

vCenter → right-click VM → Snapshots → Manage Snapshots → select your pre-patch snapshot → Delete. This KEEPS your changes — it just removes the undo point. Deleting a snapshot does NOT undo the patch.

Restore / roll back

Pick the lightest tool that fixes it:

SituationUse thisSpeed
Patch broke it, snapshot still thereRevert vCenter snapshotSeconds
Snapshot gone / VM won't bootVeeam: Instant RecoveryMinutes
Need a full clean copy backVeeam: Entire VM RestoreLonger
One file/config clobberedVeeam: Guest File RestoreMinutes

Option A — Revert the snapshot (fastest)

vCenter → Snapshots → Manage Snapshots → select pre-patch → Revert. The VM returns to its exact pre-patch state (anything changed since is gone). Delete the leftover snapshot after.

Option B — Veeam Instant Recovery (snapshot's gone)

Runs the VM directly from the backup in minutes. Veeam console → Home → Restore → VMware vSphere → Restore from backup → Entire VM restore → Instant recovery. Pick the VM + last good restore point → original location → finish.

Option C — Entire VM Restore (full clean copy)

Same path → Entire VM restore (no Instant). Select the VM + a restore point (latest or an older date) → restore to original location to overwrite the broken VM.

▸ After any restore

Re-run the health checks, confirm IDM login, and remember the box is now unpatched again. Once stable, retry the patch (new snapshot first).

Section 14

Scripts & Cron (make the box do the work)

A script is just a list of commands saved in a file so you can run them all at once. Cron is the built-in scheduler that runs a script automatically on a timer. Together they turn a 10-step chore into "set it and forget it."

Downloading things: curl vs wget

Both grab things from a web address (URL). The difference is what each is best at.

wget — "just download this file"

wget https://example.com/file.tar.gz # save it to the current folder wget -O /tmp/app.tgz https://.../file # save under a name you choose wget -c https://.../big.iso # -c = resume a broken download
(no flag)
Saves the file into the folder you're standing in. Dead simple.
-O name
Save it under a name/path you pick.
-c
Continue a download that got cut off partway.

curl — "talk to a URL or an API"

curl -O https://example.com/file.tar.gz # -O = save with its original name curl -o app.tgz https://.../file # -o = save under your name curl -I https://satellite.example.com # -I = headers only: "is it alive?" curl -s https://.../health # -s = silent, clean for scripts
-O
Save the file using its original name.
-o name
Save under a name you choose.
-I
Fetch only the headers — a quick "is this server up?" test.
-s
Silent — hides the progress meter so logs stay clean.
-L
Follow redirects if the URL forwards somewhere else.

▸ Rule of thumb

Just grabbing a file? Use wget. Checking a service, hitting an API, or scripting a health check? Use curl.

Cron: run a script on a schedule

Cron is a clock that runs commands for you. Each scheduled line is one "cron job." You manage your own jobs with crontab.

crontab -e # edit YOUR cron jobs (opens an editor) crontab -l # list your cron jobs crontab -r # delete ALL your cron jobs (careful — no undo)

The five time fields (read left to right)

* * * * * command-to-run | | | | | | | | | +-- day of week (0-6, Sunday = 0) | | | +---- month (1-12) | | +------ day of month (1-31) | +-------- hour (0-23) +---------- minute (0-59)

Real examples

0 2 * * *
Every day at 2:00 AM.
*/15 * * * *
Every 15 minutes.
0 3 * * 0
3:00 AM every Sunday.
30 23 1 * *
11:30 PM on the 1st of each month.

Wire a script into cron the right way

  1. Write your script and save it, e.g. /usr/local/bin/backup.sh.
  2. Make it runnable:
    chmod +x /usr/local/bin/backup.sh
  3. Test it by hand FIRST — fix errors now, not at 2 AM:
    /usr/local/bin/backup.sh
  4. Open your cron table:
    crontab -e
  5. Add one line — full path, and send output to a log:
    0 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
  6. Confirm it's listed:
    crontab -l

◆ The two things that trip everyone up

Full paths: cron runs with almost no PATH, so use /usr/bin/hammer, not just hammer — inside your script too. Log the output: ending a line with >> file.log 2>&1 saves both normal and error messages, so when something fails at 2 AM you can see why.

Handy scripts to keep in your back pocket

1. Dated backup of a folder (keeps the last 7)

#!/bin/bash # Back up a folder into a dated tar.gz, then delete ones older than 7 days SRC="/etc" # folder to back up DEST="/backups" # where backups go STAMP=$(date +%F) # today, e.g. 2026-08-26 tar czf "$DEST/etc-$STAMP.tar.gz" "$SRC" # make the archive find "$DEST" -name 'etc-*.tar.gz' -mtime +7 -delete # prune old ones echo "$(date): backed up $SRC" >> /var/log/mybackup.log

Point cron at it (2 AM daily) and you have automatic backups. What each line does, top to bottom: pick the source and destination, stamp today's date, tar it up, delete anything older than 7 days, then write a line to a log.

2. Warn when a disk is filling up

#!/bin/bash # Print any filesystem that is 85% full or more df -hP | awk 'NR>1 && $5+0 >= 85 {print $6, "is", $5, "full"}'

Change 85 to your threshold. Run it from cron every 15 minutes and send the output to a log or your alerting. (This is the automated version of Issue 1 in Section 12.)

3. Dated Satellite export — your core job, automated

#!/bin/bash # Run a dated incremental content export and log everything ORG="YourOrg" # your Satellite org CV="RHEL9-Base" # your Content View VER=$(date +%Y.%m.%d) # version = today's date /usr/bin/hammer content-export incremental version \ --content-view "$CV" --version "$VER" \ --organization "$ORG" --format importable \ >> /var/log/sat-export.log 2>&1

This wraps the Section 02 export in a script so a scheduled run produces a fresh, dated export every night with a full log — no typing the long command each time.

4. Restart a service if it dies (a simple watchdog)

#!/bin/bash SVC="httpd" # service to watch if ! systemctl is-active --quiet "$SVC"; then systemctl restart "$SVC" echo "$(date): $SVC was down, restarted it" >> /var/log/watchdog.log fi

Cron this every 5 minutes for a scrappy self-healing service. It checks if the service is running; if not, it restarts it and logs when it did.

Section 15

Hard & Soft Links (the thing that trips people up)

A link is just an extra name for a file. There are two kinds, and they behave very differently when you delete or move things. First, one idea that makes it all click.

The key idea: names vs. the actual data

On Linux, the real file — its data and details — lives in something called an inode (think of it as a numbered storage box on the disk). The filename you see is just a label that points at that box. Normally one label per box. Links let you have more than one.

What an inode actually is (its full purpose)

Since inodes explain everything about how links behave, here's the real definition. An inode is the filesystem's record card for a file. It holds everything about the file except two things: the file's name and its actual contents.

What's stored INSIDE an inode

Type
Whether it's a regular file, a directory, or a link.
Permissions
The read/write/execute bits (who can do what).
Owner / Group
The user and group that own it (as ID numbers).
Size
How big the file is.
Timestamps
When it was last modified, accessed, and changed.
Link count
How many names currently point at this inode — the number that makes hard links work.
Data pointers
The map to the actual blocks on disk where the contents live.

What's deliberately NOT in the inode

The filename
That lives in the directory, which is really just a table matching names → inode numbers.
The contents
Those sit in separate data blocks that the inode points to.

That split — name in the directory, everything else in the inode — is the whole trick behind links. Because the name and the inode are separate things, several names can point at one inode, and the data survives as long as the inode's link count is above zero.

ls -i file # show a file's inode number stat file # the inode number, link count, and ALL the metadata above df -i # how many inodes are used/free on each filesystem

Why it matters on the job

Finding files
The filesystem locates every file through its inode — the name is just a lookup that hands back an inode number.
Deleting
"Delete" removes a name and drops the link count by one; the data is only freed when the count hits zero. That's why a hard-linked file survives deleting one name.
Cross-drive limit
Inode numbers are unique only within one filesystem, which is exactly why a hard link can't cross drives.
Running out
A filesystem is built with a fixed number of inodes. Millions of tiny files can use them all up while disk space remains — then new files fail with "No space left on device" even though df -h shows room. Check with df -i (see Section 12).

Hard link — a second real name for the same data

A hard link is another label pointing at the same storage box (inode). Both names are equal — there's no "original" and no "copy." The data itself sticks around until the last name pointing to it is deleted.

ln realfile.txt secondname.txt # make a hard link (same data, two names)
Delete one
The other name still works and the data is fine. Data only disappears when the last name is gone.
Across drives?
No. Hard links only work within the same filesystem/drive (the box numbers are per-drive).
Link a folder?
No — hard links are for files, not directories.
Move the file?
Still works — every name points at the data box, not a location.

Soft link (symlink) — a signpost to a path

A soft link is a tiny separate file that just holds the path to another name — like a signpost that says "the real thing is over there." It doesn't point at the data box directly; it points at a name/location.

ln -s /path/to/realfile.txt linkname # make a soft link (-s = symbolic)
Delete the target
The signpost is left pointing at nothing — a "dangling" (broken) link. The link itself still exists but leads nowhere.
Delete the link
The real file is untouched. You just removed the signpost.
Across drives?
Yes. It's just a path, so it can point anywhere — another drive, another filesystem.
Link a folder?
Yes — symlinks can point at directories too. This is why they're everywhere.
Move the target?
The link breaks — the path it stored no longer leads to the file.

How to see what's what

ls -li # 1st column = inode number; hard links share the SAME number # the count after permissions = how many names point to the data ls -l # a symlink shows an arrow: linkname -> /path/to/target readlink -f linkname # print where a symlink really points stat realfile.txt # shows the inode and the "Links:" count find /home -samefile realfile.txt # find every hard link to that file

The real purpose (why they exist)

Soft links are the flexible signposts Linux runs on. The classic use is a "current" pointer you can flip to switch versions instantly — and flip back to roll back:

ln -s /opt/app/v1.2.3 /opt/app/current # apps read /opt/app/current # upgrade later by just re-pointing the signpost: ln -sfn /opt/app/v1.3.0 /opt/app/current # -f replace existing, -n don't follow into the dir

You'll see this pattern all over: systemctl enable works by creating symlinks, and /etc/alternatives uses them to pick the default java or python. They also let you put a file where a program expects it without actually moving the real file.

Hard links give you two names for one set of data with no extra disk space. The big real-world use is snapshot-style backups (like rsync --link-dest): files that didn't change between backups are hard-linked instead of copied, so ten daily "full" backups can share one copy of every unchanged file and take a fraction of the space.

▸ The one-line summary

Hard link = another real name for the same data (same drive, survives if you delete the other name). Soft link = a signpost to a path (works across drives and folders, breaks if the target moves or is deleted). When in doubt, use ln -s — it's the flexible one you'll reach for 95% of the time.

STIG & SCAP Compliance (hardening RHEL)

A STIG is DISA's security-hardening checklist for a system. SCAP is the machine-readable version a scanner can check automatically. This tab: what the pieces are, how to run a scan, where the result files go, and the tools — including the Navy ones — that make it easier. First rule: snapshot before you harden (Section 13), because some fixes can break a box.

The vocabulary (plain terms)

STIG
Security Technical Implementation Guide — DISA's list of required settings to lock a system down.
SCAP
The automatable file format for those checks, so a tool can scan instead of a human eyeballing each one.
SSG
SCAP Security Guide — the actual RHEL content (profiles + checks) you scan against. Ships as a package.
OpenSCAP / oscap
The scanner built into RHEL that runs the SSG content.
CKL
The checklist file an assessor opens in DISA STIG Viewer — your evidence, marked Open / Not a Finding / N/A.
CAT I/II/III
Severity of a finding — fix CAT I (high) first.

Run a STIG scan with OpenSCAP (built into RHEL)

Install the scanner + content, then confirm the STIG profile is present:

dnf install -y openscap-scanner scap-security-guide oscap info /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml | grep -i stig

Run the scan — it writes a machine-readable XML and a human-readable HTML report:

mkdir -p /var/log/compliance oscap xccdf eval \ --profile xccdf_org.ssgproject.content_profile_stig \ --results /var/log/compliance/stig-results.xml \ --report /var/log/compliance/stig-report.html \ /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml
--profile …stig
Use the DISA STIG baseline (swap in cis, ospp, or pci-dss for other standards).
--results
The XML — the data file you archive or feed to other tools.
--report
The HTML you actually open and read, with findings grouped by STIG ID.
ssg-rhel9-ds.xml
The content datastream. Use ssg-rhel8-ds.xml on RHEL 8.

▸ Make a STIG Viewer file

Add --stig-viewer results-stig.xml to the eval to produce a file you import into DISA STIG Viewer (then Import STIG to match it up). That's what turns a raw scan into the CKL-style artifact an assessor wants.

Get the files to/from your repository

In an air-gapped shop the flow mirrors Section 02: the SSG content and DISA benchmarks come IN from your repo/Satellite, and the results go BACK to a compliance share.

# pull the STIG benchmark/content from your internal repo (example) curl -O https://repo.example.com/stig/ssg-rhel9-ds.xml # ...run the scan... then send the results back to the compliance share scp /var/log/compliance/stig-report.html ian@repo.example.com:/compliance/web01/

Scan a remote box without an interactive login:

oscap-ssh ian@web01.example.com 22 xccdf eval \ --profile xccdf_org.ssgproject.content_profile_stig \ --report /tmp/web01-stig.html \ /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

Auto-remediation (careful!)

OpenSCAP can generate fix scripts from the same profile. Generate, review, snapshot, then apply — never blind-apply in production.

# build an Ansible playbook of fixes (also: --fix-type bash) oscap xccdf generate fix \ --profile xccdf_org.ssgproject.content_profile_stig \ --fix-type ansible \ /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml > stig-remediate.yml

The tools you'll hear about (incl. the Navy ones)

OpenSCAP (oscap)
Built into RHEL. Free, scriptable, great for continuous scanning — what the commands above use.
SCC
SCAP Compliance Checker — DISA's scanner, authored by the Navy's NIWC Atlantic. Common across DoD; produces a compliance score + results. (niwcatlantic.navy.mil/scap)
Evaluate-STIG
The Navy tool (NAVSEA / NSWC Crane). A PowerShell script that auto-detects which STIGs apply to a host, runs the checks, and writes the CKL/CKLB checklist for you — turning hours of manual box-ticking into one run. Runs on Linux and Windows. It's a checklist generator, not a vulnerability scanner.
DISA STIG Viewer
The official manual tool to open and annotate CKL checklists — the "system of record" you submit to your ISSO.

✓ Why Evaluate-STIG is loved

It kills the "paperwork fatigue" — instead of hand-checking every passing item in STIG Viewer, it fills the checklist automatically so you focus on the actual open findings.

What can break a box (handle with care)

Some STIG settings are aggressive. Always snapshot first (Section 13), test in Dev, and review fixes rather than blanket-applying them.

SELinux
Keep it Enforcing — the STIG requires it, and disabling it both fails the STIG and removes protection. Fix denials with policy, don't turn it off. (Check with getenforce.)
FIPS mode
Enabling FIPS crypto can break older clients/protocols and some apps — test connectivity right after.
Mount options
Strict noexec/nosuid on /tmp, /var, etc. can stop software that expects to run there.
Lockout / password rules
Aggressive lockout can lock out service accounts and even you — know the unlock path before you apply it.
Disabled ciphers
Turning off older SSH ciphers/TLS can cut off legacy systems that only speak the old ones.

◆ The safe loop

Snapshot → scan (oscap) → read the report → apply fixes a few at a time → re-scan → confirm the box still works → generate the CKL for your ISSO. We can expand later on exactly which STIG IDs bite hardest and how to document exceptions.

Networking (nmcli): IPs, DNS & config

On RHEL 8/9 the network is run by NetworkManager, and the everyday tool is nmcli. Editing old ifcfg files by hand is out — nmcli writes the config for you and applies it cleanly. This is daily-driver stuff: see an IP, change an IP, fix DNS.

See what you've got

nmcli # everything: devices, connections, IPs, DNS nmcli device status # each NIC and whether it's connected nmcli connection show # the saved "connections" (config profiles) ip a # quick raw view of interfaces + IPs ip r # the routing table (your default gateway)
device
The physical NIC (e.g. ens192).
connection
A saved config profile applied to a device. You edit the connection, not the device.

Change to a static IP

Say the connection is named "ens192". Set address, gateway, and DNS, switch it to manual, then bring it up:

nmcli con mod "ens192" ipv4.addresses 10.1.1.50/24 nmcli con mod "ens192" ipv4.gateway 10.1.1.1 nmcli con mod "ens192" ipv4.dns "10.1.1.10,10.1.1.11" nmcli con mod "ens192" ipv4.method manual nmcli con up "ens192" # apply it now
con mod
Modify a saved connection (writes the config).
ipv4.addresses
The IP plus its subnet size (/24 = 255.255.255.0).
ipv4.method manual
Static. Use auto for DHCP instead.
con up
Activate the connection so the change takes effect.

Just change DNS

# replace the DNS servers nmcli con mod "ens192" ipv4.dns "10.1.1.10,10.1.1.11" # set the search domain nmcli con mod "ens192" ipv4.dns-search "example.com" nmcli con up "ens192" # verify what's actually in use resolvectl status cat /etc/resolv.conf

◆ Don't hand-edit /etc/resolv.conf

NetworkManager rewrites it. Set DNS with nmcli so it sticks across reboots, then read resolv.conf only to confirm.

Switch back to DHCP

nmcli con mod "ens192" ipv4.method auto nmcli con up "ens192"

Hostname & the hosts file

hostnamectl # show current hostname hostnamectl set-hostname web01.example.com # set it cat /etc/hosts # static name-to-IP mappings live here

Config files worth knowing (but edit via nmcli)

/etc/NetworkManager/ system-connections/
Where nmcli saves connection profiles on RHEL 9 (keyfile format).
/etc/hostname
The system hostname (set it with hostnamectl).
/etc/hosts
Manual name→IP entries, checked before DNS.
/etc/resolv.conf
The active DNS resolvers — generated, don't edit by hand.

▸ The everyday loop

nmcli con mod "<conn>" <setting> <value> to change it → nmcli con up "<conn>" to apply → ip a / resolvectl status to confirm. That's 90% of the network changes you'll ever make.

Section 18

Ansible from Scratch

Ansible runs the same setup steps on many servers at once, from one control box, over SSH — no agent to install on the targets. You describe what you want in a plain-text file (a "playbook"), and Ansible makes each server match it. We'll build it up line by line.

Install it (on your control box only)

dnf install -y ansible-core ansible --version

The three pieces

Inventory
A list of the servers to manage, grouped by role.
Playbook
A YAML file describing the tasks to run.
Modules
The building blocks (install a package, start a service, copy a file…). You call modules instead of writing shell.

Step 1 — an inventory file

Make a file called inventory.ini. Names in brackets are groups; list hosts under them:

[web] web01.example.com web02.example.com [db] db01.example.com

Test that Ansible can reach them (it uses your SSH key from Section 06):

ansible -i inventory.ini web -m ping

A green "SUCCESS" / "pong" from each host means you're good.

Step 2 — your first playbook, line by line

Make site.yml. Every line matters — 2-space indentation, no tabs:

--- - name: Set up the web servers # a friendly name for this "play" hosts: web # which inventory group to run on become: yes # run as root (via sudo) tasks: # the list of steps - name: Install Apache # step 1 — a friendly label ansible.builtin.dnf: # the module (dnf = packages) name: httpd # which package state: present # "present" = make sure it's installed - name: Start and enable Apache # step 2 ansible.builtin.service: # the service module name: httpd state: started # make sure it's running enabled: yes # and starts on boot
---
Marks the start of a YAML file.
- name:
A human label (for plays and tasks). Always include it.
hosts:
Which group from your inventory to target.
become: yes
Do it as root (sudo) — needed to install packages, etc.
tasks:
The ordered list of steps; each is one module call.
state:
You declare the END STATE you want; Ansible figures out how to get there and skips work already done.

Step 3 — run it

ansible-playbook -i inventory.ini site.yml # preview without changing anything: ansible-playbook -i inventory.ini site.yml --check # more detail when something fails: ansible-playbook -i inventory.ini site.yml -v

◆ YAML rules that bite beginners

Spaces only, never Tabs. Indent 2 spaces per level, consistently. A list item starts with - . key: value needs the space after the colon. 90% of "why won't it run" is indentation.

Ad-hoc commands (no playbook needed)

Run one thing across every host right now:

ansible -i inventory.ini all -a "df -h" # run a command everywhere ansible -i inventory.ini all -m dnf -a "name=vim state=present" --become

Real-world playbooks you'll actually use

1. Patch everything (and reboot if needed)

--- - name: Patch all servers hosts: all become: yes tasks: - name: Update every package ansible.builtin.dnf: name: "*" state: latest - name: Reboot only if the update needs it ansible.builtin.reboot: when: ansible_reboot_pending | default(false)

2. Create a user and push your SSH key everywhere

--- - name: Add an admin user hosts: all become: yes tasks: - name: Create the user ansible.builtin.user: name: jdoe groups: wheel append: yes - name: Install their SSH key ansible.posix.authorized_key: user: jdoe key: "{{ lookup('file', '/path/jdoe.pub') }}"

Modules named ansible.posix.* or community.* come from a collection — install once with ansible-galaxy collection install ansible.posix.

3. Push a config file, then restart the service

--- - name: Deploy chrony config hosts: all become: yes tasks: - name: Copy the config ansible.builtin.copy: src: files/chrony.conf dest: /etc/chrony.conf notify: restart chrony # triggers the handler below handlers: - name: restart chrony ansible.builtin.service: name: chronyd state: restarted

A handler only runs if a task "notifies" it — so the service restarts only when the file actually changed.

▸ Where to grow next

Group variables in group_vars/, template config files with the template module (Jinja2), and bundle reusable playbooks into roles. But inventory + playbook + ansible-playbook is the whole core — everything else is convenience.

Golden Images & Templates (RHEL → vCenter)

Build one hardened, fully-configured RHEL box once, turn it into a template, then spin up new servers from it in minutes — each coming up with your baseline already in place. Two ways: convert a VM to a vCenter template, or build an image file with RHEL Image Builder and upload it.

Way 1 — build a VM and convert it to a template

  1. Build the base VM in vCenter: create a VM, install RHEL (from ISO, or automated with Kickstart below).
  2. Configure it the way every server should start: register to Satellite, patch, install your standard agents/software, set baseline configs, harden it (STIG, Section 16).
  3. Generalize it — strip machine-specific identity so clones aren't duplicates (cleanup box below).
  4. Convert to template: shut it down, then in vCenter right-click → Template → Convert to Template (Section 10).
  5. Deploy new servers from it with a Customization Spec for a unique hostname/IP (Section 10).

◆ Generalize before you template (run on the VM first)

Otherwise every clone shares an identity and they'll fight on the network.

# clear the unique machine ID (regenerates on next boot) truncate -s 0 /etc/machine-id # remove SSH host keys (each host regenerates its own on boot) rm -f /etc/ssh/ssh_host_* # clean caches, logs, and history dnf clean all rm -f /root/.bash_history # then shut down and convert to template in vCenter poweroff

Way 2 — build an image with RHEL Image Builder

Image Builder turns a "recipe" (packages + settings) into a ready image file you upload to vCenter. It's in the web console (Cockpit → "Image Builder") or the composer-cli command line.

dnf install -y osbuild-composer composer-cli cockpit-composer systemctl enable --now osbuild-composer.socket # see the available output types composer-cli compose types # build a vSphere image from a blueprint you defined (e.g. rhel9-base) composer-cli compose start rhel9-base vmdk composer-cli compose status # wait for FINISHED composer-cli compose image COMPOSE-UUID # download the .vmdk

Then upload the .vmdk/.ova into vCenter (Deploy OVF/OVA, or attach the vmdk to a new VM) and convert that to a template. Now it's a one-click deploy.

blueprint
Your recipe — the packages, users, and settings the image should contain (built in the web console or a TOML file).
vmdk / ova
The vSphere-friendly output formats — pick these so vCenter can use the image directly.

Automated installs — Kickstart (the base of it all)

A Kickstart file answers every installer prompt (disk layout, users, packages, network) so RHEL installs hands-free — the foundation for repeatable base builds. In a Satellite shop it's served for you; standalone, point the installer at it:

# at the RHEL installer boot prompt, feed it a kickstart: inst.ks=https://repo.example.com/ks/rhel9-base.ks

▸ Which way to choose

Convert-a-VM-to-template is the simplest and most common in a vCenter shop — do that first. Image Builder shines when you want the image defined as code and rebuilt automatically. Kickstart underpins both by making the base install repeatable.

Mail Relay Server (Postfix)

A mail relay is one server that all your other boxes hand their outgoing mail to, which then forwards it up to your real mail gateway (the "smarthost"). It's how servers send alerts, cron output, and reports without each one talking out directly. RHEL's tool is Postfix.

Two roles — know which you're building

The relay
Accepts mail from your internal servers and forwards it upstream. This is the "mail relay server."
A null client
Every other server, set to send ALL its mail to the relay and nothing else.

Build the relay server

  1. Install Postfix and start it:
    dnf install -y postfix systemctl enable --now postfix
  2. Edit /etc/postfix/main.cf — the key settings:
    # who this server is myhostname = mailrelay.example.com mydomain = example.com myorigin = $mydomain # listen on all interfaces so other servers can reach it inet_interfaces = all inet_protocols = ipv4 # WHO may relay through it — your internal networks ONLY mynetworks = 127.0.0.0/8, 10.0.0.0/8 # where to forward everything (your upstream smarthost/gateway) relayhost = [smtp-gw.example.com]:25 # don't accept local delivery for other domains mydestination = $myhostname, localhost
  3. Open the SMTP port and restart:
    firewall-cmd --permanent --add-service=smtp firewall-cmd --reload systemctl restart postfix

✕ Don't build an open relay

mynetworks must list only your trusted internal ranges. Allow the world and spammers will use your server and get you blocklisted. Keep it tight.

If the upstream needs a login (SASL auth)

# add to main.cf: smtp_sasl_auth_enable = yes smtp_sasl_password_maps = hash:/etc/postfix/sasl_passwd smtp_sasl_security_options = noanonymous # create the password file, hash it, lock it down: echo "[smtp-gw.example.com]:25 user:password" > /etc/postfix/sasl_passwd postmap /etc/postfix/sasl_passwd chmod 600 /etc/postfix/sasl_passwd* systemctl reload postfix

Point the other servers at it (null client)

On each sending server, set just these in /etc/postfix/main.cf, then reload:

relayhost = [mailrelay.example.com]:25 inet_interfaces = loopback-only # don't accept inbound mail mydestination = # deliver nothing locally
systemctl reload postfix

Test it & watch the log

dnf install -y s-nail # provides the 'mail' command echo "relay test" | mail -s "test from web01" you@example.com tail -f /var/log/maillog # watch it hand off, or show the error

▸ After any main.cf change

Run postfix check for syntax, then systemctl reload postfix. Read /var/log/maillog — it tells you exactly why a message did or didn't relay.
